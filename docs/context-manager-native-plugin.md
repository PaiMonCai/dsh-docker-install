# billion-context 内置原生插件

插件随本项目镜像提供，使用固定上游 Kernel，通过 DSH 的 Agent、ToolRuntime、
CompactionEngine 和原生 Session 工作。无需额外安装 npm 插件、启动代理或重新配置模型。
当前接入入口是本项目的 Web 启动器；直接运行其他 DSH Profile 保持原有行为。

## 启用与停用

1. 在 Web 的「设置 → 上下文管理」开启「启用原生上下文增强」。
2. 按需选择 CCR 大工具结果原文回取，点击「保存设置」。
3. 使用现有实例管理方式重启容器，例如 `dshd restart`。
4. 返回「运行状态」，查看各预设是「原生增强已挂载」、等待挂载，还是保留原生配置。

设置页会区分已保存的目标与本次启动的配置。运行中的 Agent 不会在请求执行到一半时
更换压缩器。启停、参数和规则修改都在重启后统一应用；不需要设置 Tiered、ACP、CCR
实验环境变量。旧实验入口继续兼容，但不能与新的总开关同时使用。

停用时关闭同一个总开关，保存并重启。预设恢复其原有配置，不把管理页的预算参数
强加给已停用的原生压缩。Session 日志不迁移、不删除；带有旧 ACP/CCR 记录的会话
会获得同会话只读回取工具，新建的普通原生会话不增加这些工具。原文不会因为停用而
被写回模型活动上下文，后续是否读取由工具调用和 DSH 权限控制决定。
原生压缩随后再次折叠旧 ACP 摘要时，历史原文仍可通过只读工具检索和分页回取。

## 原生兼容边界

- 启动器通过官方 `--dump-config` 读取实际组合，保留已有依赖注入，使用临时
  `--patch` 叠加启动顺序。不会把生成补丁写入用户 Profile。
- 总开关默认关闭。缺少新开关的旧配置只作为历史策略意图读取，不会自动激活。
- 开启后，只替换具有唯一 Basic 压缩器及原生 `/compact` 入口的兼容预设。
  其他插件、模型路由、工具及权限配置保留；媒体与复杂工具消息继续受保护。
- 预设没有压缩器、具有重复或条件压缩器、存在外部 billion-context，或配置混合模型
  引擎时，保留该预设原配置并显示原因。不会为缺少压缩器的自定义预设强塞一个引擎。
  Reverse 等自定义预设是否可用以各自状态为准，不能从同一镜像的 Standard 状态推断。
- 自动压力、超窗恢复和手动压缩仍由原生引擎的事务与锁管理。普通增强摘要失败时，
  回退到原生摘要；取消仍然中止。模型提交的 ACP 范围继续经过原生事务验证。
- CCR 只在原文持久化成功后缩减结果。不可安全处理的内容保持完整结果。
- 管理页的跨会话原文浏览继续默认关闭；总开关不授予共享历史或多用户访问权限。

检测外部插件仅覆盖可观测的配置和已知路由特征，不能证明远端网关没有进行上下文处理。
不要在同一模型链路叠加外部 billion-context 压缩。

## 验证与真实 Provider 对照

本地与 CI 的固定模型适配器用于验证原生执行链，不证明真实节费或长会话质量。
生命周期烟雾入口为：

```bash
bash tests/test-context-manager-native-plugin.sh IMAGE standard
```

它创建一次性数据卷，完成启用、停用、冷读原文及重新启用，不读取真实会话或请求收费模型。
镜像构建还运行真实 AgentLoop / ToolRuntime，验证 ACP 提交、CCR 持久化、只读回取的
作用域隔离及原生工具拒绝策略。

真实 Provider 对照由实例所有者单独执行：

1. 在隔离实例中固定同一镜像、模型、模型参数和两个可重复的长任务，分别选择代码维护
   与大结果阅读。任务只使用合成或已授权数据，设置费用与时长上限。
2. 关闭增强并重启，分别创建新会话运行任务，记录完成质量、错误、模型账单用量和延迟。
3. 开启增强并重启，以相同输入创建独立会话运行同样的任务。用 `acp_cache` 查看该会话
   账本，并实际分页回取至少一个压缩块和一个 CCR 原文，比较原始数据。
4. 启用和停用后分别验证 `/compact`、超窗恢复、取消、重启续接和相关 Preset 工具功能。
   只保存去标识的结果，不把真实消息、密钥或工具原文上传到 PR。
5. Provider 缺失的缓存计数记作未知。`acp_cache` 中的相对经济估算不能替代 Provider
   实际账单；当前原生流时间不包含请求派发时间，不声称测得首 token 延迟。

运行状态中的已挂载只证明当前组合，不代表真实 Provider 验收或生产准入通过。

## 来源

算法来自 ranxianglei 的 [billion-context](https://github.com/ranxianglei/billion-context)
和 [acp-kernel](https://github.com/ranxianglei/acp-kernel)。固定来源、可重复构建与许可证
保存在插件的 `vendor/` 目录中。此次工作不升级或改写上游 Kernel 算法。

实现计划与当前验证记录见 [原生插件交付计划](context-manager-native-plugin-plan.md)。
