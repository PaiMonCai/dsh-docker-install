# DSH Docker：终端 → Web 管理迁移（第一批架构契约）

> 状态：Phase 1 基线清单；Phase 2 增量已另列 [第二批实施记录](web-management-phase2.md)。以下表格保留第一批审计时的原始状态，不能作为第二批上线后的当前功能统计。
>
> 状态：Phase 1 实施。此文按 `dshd 0.12.1` 的六大类 / 40 个二级菜单项、当前 `dsh-instance-manager` 和宿主机执行器建立基线。状态表中“Web 待迁移”表示**尚未实现**，不代表已有 Web 操作。没有在第一批直接删除任何 CLI 命令。

## 目标与不在本批范围内的事项

- 目标：Web 成为日常运维界面；`dshd` 保留独立安装、卸载、故障恢复入口，同时继续作为受控宿主机执行引擎。
- 目标：原有 Web 能力与宿主机执行器使用可核对的**操作名称、参数形状、状态集合**；新的 Web 可以获知当前宿主机支持的操作并禁用不支持的入口。
- 目标：建立逐项迁移清单，避免日后把独立功能遗漏或重复实现。
- 不在本批范围：增加高风险写权限、多实例写接口、任意 Shell、原始配置文件编辑、删减现有 CLI 菜单、重新设计 Web 界面或改动 Docker Socket 授权。

## 归属：一套执行逻辑、两种交互入口

| 层 | 负责事项 | 不负责事项 |
|---|---|---|
| `install.sh` | 下载安装 `dshd` | 长期管理/配置持久化逻辑 |
| `dshd` | 宿主机实际安装、实例操作、网络、备份、恢复、Web 救援等**实现**，以及 CLI 故障入口 | 作为 Web 的授权来源或绕开已有锁 |
| `docker/plugins/dsh-instance-manager` | 已认证 Web 交互、输入限制、任务提交、任务状态/日志展示、能力识别 | 直接获得 Docker Socket、任意 Shell/宿主机配置文件 |
| `docker/dsh-web-manager.py` | 固定实例的白名单执行器、串行队列、状态落盘、自动更新检测、日志采集；**最终执行授权点** | 从浏览器参数选择宿主机命令、目标实例 ID、自由镜像 URL 或路径 |
| `docker/management-operations.json` | 仓库内可审计的 Web 操作清单与测试源 | 运行时加载的动态权限配置；不能由 Web 用户编辑来增加权限 |

执行链路：

```text
DSH Web (已认证会话)
  → dsh-instance-manager (校验、能力协商)
  → requests/<uuid>.json (受限只写挂载)
  → 宿主机 dsh-web-manager.py (固定实例、二次校验、持久化任务)
  → dshd <已允许的命令参数> → Docker / 本机状态
  → results/<uuid>.json + status.json (只读映射到容器)
  → DSH Web 状态恢复
```

**不可突破的边界**：没有通用 `command`/`shell`/`path`/`instanceId` 参数；Web 不选择任意管理目标，不挂载 Docker Socket，不把代理链接、Token 或密钥写进公开任务日志。现有队列与数据目录挂载规则继续以 [Web 实例管理](web-management.md) 为准。

## Phase 1 的操作能力契约

仓库清单：[`docker/management-operations.json`](../docker/management-operations.json)，schema 为 `dsh-web-management-operations/v1`。目前只登记**已经上线**的 16 种 Web 任务。后续扩展时，必须同时更改清单、Node 校验、Python 白名单与对应测试；不能只给前端增加按钮。

- 宿主机状态快照增量提供 `management: { schema: 1, operations: [...] }`。这是供 Web 展示的**能力信息**，实际允许执行什么仍由 Python `command_for` 和 `validate_settings` 决定。
- Node `HostBridge.submit` 在现有参数校验之后，拒绝宿主机未公布支持的任务（`host-operation-unavailable`）；前端禁用此类按钮，并对直接操作给出升级宿主机提示。
- **兼容旧版宿主机**：旧执行器没有 `management` 字段时，继续使用原有 Node 白名单和宿主机自身最终校验，避免升级 Web 镜像后把既有管理入口全部禁用。新宿主机声明未知 schema 时则拒绝任务。
- 不把清单 JSON 放进宿主机的受控配置路径，也不把可写的清单当作动态授权表。当前采取“清单 + 双端测试校验”防漂移，后续有明确部署/签名机制再考虑统一生成代码。

### 任务状态和生命周期

| 状态 | 含义 | 是否可以自动重放 |
|---|---|---|
| `queued` | Web 已持久提交，等待后台领取 | 不能在客户端重复生成新 ID |
| `running` | 宿主机领取任务并持久化启动状态 | 否 |
| `succeeded` | 执行器返回成功 | 不需要 |
| `failed` | 任务校验/命令运行失败，错误经脱敏 | 否，需人工检查后决定 |
| `interrupted` | 执行器重启时发现未完成任务 | **严禁自动重放**，先确认宿主机真实状态 |

已有边界继续保持：任务超过 10 分钟不得在长时间离线后执行；按实例串行并依赖宿主机锁；最近任务记录限量保留；Web 断线后由宿主机完成更新和健康检查；相同 UUID 重试提交遵循幂等保护。成功回滚只恢复镜像/容器，不自动回滚数据卷。操作日志须脱敏且有上限。

## 后续批次的准入标准

1. **先实现执行器契约**：为每项新功能定义参数格式、作用域、超时、敏感数据、危险操作确认以及事务/回滚策略，严禁前端拼接 Shell 命令。
2. **再开放 Web 接口**：按已存在的鉴权与同源控制提交任务，界面只显示被宿主机授权的能力。多实例统一管理必须引入独立的宿主机授权模型。
3. **同时补回归**：Node 请求验证、Python 执行器拒绝非法参数、离线/断线恢复、实机临时容器更新与回滚。恢复与卸载涉及数据破坏，测试必须在临时卷中。
4. **最后删终端交互项**：Web 完成验证后只精简 `menu_render_*` 与菜单路由，不删除 Web 依赖的 `cmd_*`/CLI 子命令；保留一套可独立于 Web 运行的救援路径。

## 已知设计风险（留待后续批次）

- 当前 `dshd restore` 会清理现有数据后解压备份，没有先完成独立验证；未来 Web 恢复流程必须先实现安全预检与失败保护。
- 目前卸载会先处理 Dashboard，不能把相同的动作顺序搬进 Web；本计划把卸载限定到 CLI。
- Web 实例管理通道依赖 DSH 自身认证，当前并非多租户角色系统；在真正增加敏感配置写入前应增强管理员授权审计。
- 停止运行 DSH 自身会失去 Web 页面；停机后恢复必须依靠宿主机命令或独立控制面，不能假装容器中的 Web 能自行唤醒。
