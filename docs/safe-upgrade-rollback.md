# DSH Docker 安全升级与应用版本回滚

## 设计边界

`dshd update` 和 `dshd recreate` 对已存在的容器执行**两阶段替换**：

1. 先拉取目标镜像，检查 Sidecar、运行参数、挂载源。
2. 停止旧 `dsh`，将旧容器改名为 `dsh-rollback`，**不删除**旧容器或其镜像层。
3. 创建新版容器，等待 DSH Web 启动，并要求 Docker HEALTHCHECK 真正达到 `healthy`。
4. 成功则保留已停止的 `dsh-rollback`，之后可以手动退回旧版本；**仅在新容器成功后**更新 `dshd` 配置文件。
5. 若创建、启动或健康检查失败，自动删除失败的新容器，把旧容器恢复原名并启动。原持久化卷没有被删除或覆盖。

没有旧容器的新安装沿用常规创建流程。当前阶段保留**最多一个旧版回滚点**；再次升级前必须先选择回滚或执行 `dshd rollback clear`，避免默默覆盖上一版。

## 使用

```bash
dshd update
dshd rollback status
dshd rollback          # 回到旧版容器（需要交互确认）
dshd rollback clear    # 删除保留的旧版容器（需要交互确认）
```

`rollback` 只切换停止/运行的应用容器。成功后将本机 `DSH_IMAGE` 指向实际运行的旧镜像 ID，避免下一次手动重建悄悄运行已经更新的 tag。更新失败时原配置文件不被覆盖。已回滚时升级后的容器会保留在 `dsh-rollback-failed`，供排障后手动检查/清理（**删除容器时不要加 `-v`**）。

## 数据安全注意事项

- **绝不自动回退或覆盖持久化的数据卷**：`/root/.dsh`、`/workspace`、额外挂载以及会话数据会保持当前内容。镜像回滚不是数据库快照回滚。
- 如果新版 DSH 修改了持久化数据格式，旧版本可能无法读取；此时回滚健康检查会失败，并尝试恢复升级后容器。**涉及不可逆数据迁移的版本，升级前仍然需要独立备份数据。**
- 该功能不自动移除数据库、第三方插件或网络 Sidecar；也不保证 Sidecar 版本与旧镜像必然兼容。
- `dshd rollback clear` 只删除停止的旧容器，不删除卷、工作区或镜像层；没有足够回滚空间时，应先确认当前镜像稳定，再清理旧容器。
- 未通过官方容器健康检查的新镜像会自动恢复旧容器；浏览器插件专项验证由独立的 CI/诊断负责，不应把 HTTP 端口可访问等同于完整 UI 功能正常。

验证：`tests/test-dshd-rollback.sh` 覆盖手动回滚、容器恢复、旧版本固定及更新失败后不写入新的配置。
