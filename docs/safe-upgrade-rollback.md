# DSH Docker 安全升级与应用版本回滚

## 设计边界

`dshd update` 和 `dshd recreate` 对已存在的容器执行**两阶段替换**：

1. 先拉取目标镜像，检查 Sidecar、运行参数、挂载源。
2. 停止旧 `dsh`，将旧容器改名为 `dsh-rollback`，**不删除**旧容器或其镜像层。
3. 创建新版容器，等待 DSH Web 启动，并要求 Docker HEALTHCHECK 真正达到 `healthy`。
4. **仅在新容器成功后**保存 `dshd` 配置文件，再自动清理当前实例已停止的回滚容器，并尝试删除这些容器释放出来的旧镜像。
5. 若创建、启动或健康检查失败，自动删除失败的新容器，把旧容器恢复原名并启动。原持久化卷没有被删除或覆盖。

没有旧容器的新安装沿用常规创建流程。默认更新成功后不保留手动回滚点，更新失败时仍会自动恢复刚刚替换的旧容器。已有的 `dsh-rollback` 不再阻止正常更新：本次旧容器先暂存在 `dsh-rollback-pending`，已有回滚点保留到更新成功后一起清理；更新失败则保留原回滚点。若暂存位置已存在，脚本会停止更新，要求先检查中断遗留的容器。

## 使用

```bash
dshd update
dshd recreate                    # 同样在成功后自动清理
DSHD_KEEP_ROLLBACK=1 dshd update   # 本次保留手动回滚点及其镜像
dshd rollback status              # 列出回滚点和遗留候选容器
dshd rollback                     # 回到保留的旧版容器（需要交互确认）
dshd rollback clear               # 清理停止的回滚容器及旧镜像（需要交互确认）
```

`DSHD_KEEP_ROLLBACK` 默认为 `0`，仅接受 `0` 或 `1`，可通过命令环境或 shell 的 `export` 设置；也适用于 `recreate`。设为 `1` 时沿用保留一个手动回滚点的行为，下一次同样启用保留模式的更新需要先处理已有回滚点。恢复默认模式后，下次成功更新会自动清理之前保留的回滚资源。Standard、Research 和 Reverse 均通过同一流程清理各自实例的资源。

`rollback` 只切换停止/运行的应用容器。成功后将本机 `DSH_IMAGE` 指向实际运行的旧镜像 ID，避免下一次手动重建悄悄运行已经更新的 tag。更新失败时原配置文件不被覆盖。已回滚时升级后的容器会保留在 `dsh-rollback-failed`，供排障后执行 `dshd rollback clear`，或在下次成功更新后自动清理。

## 数据安全注意事项

- **绝不自动回退或覆盖持久化的数据卷**：`/root/.dsh`、`/workspace`、额外挂载以及会话数据会保持当前内容。镜像回滚不是数据库快照回滚。
- 如果新版 DSH 修改了持久化数据格式，旧版本可能无法读取；此时回滚健康检查会失败，并尝试恢复升级后容器。**涉及不可逆数据迁移的版本，升级前仍然需要独立备份数据。**
- 该功能不自动移除数据库、第三方插件或网络 Sidecar；也不保证 Sidecar 版本与旧镜像必然兼容。
- 自动清理仅在当前实例运行且健康时进行，且在配置保存之后；失败不会把已成功的更新报告为失败。配置保存失败时不清理回滚资源。
- 清理仅匹配当前实例的 `-rollback`、`-rollback-pending`、`-rollback-failed` 三个完整容器名，并检查实例标签和停止状态。不会强制停止或删除正在运行的候选容器，也不会清理其他实例的容器。
- 旧镜像按已删除回滚容器的不可变镜像 ID 去重后删除，不使用强制删除、全局 prune 或卷删除。当前镜像、被其他容器引用的镜像、有多个标签的镜像会保留，共享的无标签父镜像也不会递归清理。清理失败会给出提示；若容器已删除但镜像仍保留，后续可根据提示的镜像 ID 检查引用并单独清理。
- 未通过官方容器健康检查的新镜像会自动恢复旧容器；浏览器插件专项验证由独立的 CI/诊断负责，不应把 HTTP 端口可访问等同于完整 UI 功能正常。

验证：`tests/test-dshd-rollback.sh` 覆盖手动回滚、容器恢复、旧版本固定、更新失败保留旧回滚点、成功后清理及重复更新、保留模式、保存配置失败、实例隔离、共享镜像与数据卷保护。
